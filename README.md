# Editora website

The marketing + documentation site for [Editora](https://github.com/adriandeleon/Editora),
a keyboard-driven, cross-platform programmer's text editor. Live at
**[editora-project.dev](https://editora-project.dev)**.

Built with [Astro](https://astro.build) and deployed to GitHub Pages via
`.github/workflows/pages.yml` on every push to `master`.

Editora is built with the help of AI coding tools.

## Develop

```bash
npm install
npm run dev       # http://localhost:4321
npm run build     # production build to dist/
npm run preview   # serve the build
npm run check:docs       # command ids and Emacs chords quoted in the docs (also run by build)
npm run check:generated  # every generated page still matches the Editora release (needs JDK 25)
npm run check:links      # internal links and anchors in dist/ (after a build)
```

Every pull request runs `.github/workflows/check.yml`: `check:generated`, then
`check:docs`, the build, and `check:links`. The deploy workflow
(`.github/workflows/pages.yml`) runs `check:generated` before it builds, and the
build runs `check:docs`, so the site is not deployed with a page that no longer
matches the app or quotes a command id or chord the app does not have.

`check:generated` (`scripts/check-generated.mjs`) runs every generator below
against Editora at the tag of the release `src/lib/version.ts` names
(`v<version>`) and fails when the output differs from what is committed. It
takes the tag from a local Editora clone when it has it (`git archive`, so the
clone's branch is untouched), else a shallow clone from GitHub; pass
`-- --editora <dir>` for a tree already at that release. It rewrites the
generated files in place, so `git diff` shows the difference afterwards. A
version with no tag yet (a draft of the next release on `website-next`) fails
it unless `--allow-unreleased` is given, which `check.yml` passes for pull
requests into any branch but `master`.

## Content

Most content is Markdown under `src/content/`:

- `docs/` — documentation pages (sidebar grouped by `category` + `order`),
  **copied from Editora** (see below): edit them in Editora's `user-docs/guide/`
- `news/` — release-style announcements
- `features/` — one page per feature (also drives the home-page grid)

Add a Markdown file with the right frontmatter and it appears automatically;
lists, the sitemap, and RSS regenerate on the next build.

Feature screenshots go in `public/screenshots/features/<slug>.png` (the slug
matches the page URL, e.g. `/features/git` → `git.png`).

## Generated data

The generators are JDK 25 compact source files (JEP 512), run with `java`, no
build step. Run them from the repo root.

The user guide is Editora's: its source is the
[`user-docs/`](https://github.com/adriandeleon/Editora/tree/master/user-docs) folder of the Editora repository,
so a change to the app and the page that describes it land in one pull request, and the app ships the same
pages for reading offline. `java scripts/SyncDocs.java` mirrors it here:
`user-docs/guide/` → `src/content/docs/`, `user-docs/commands/` → `src/content/command-docs/` and
`user-docs/screenshots/docs/` → `public/screenshots/docs/` (a file removed there is removed here). It keeps
`src/content/docs/pauta.md` (GenPauta's) and `public/screenshots/docs/thumbs/` (gen-thumbs'). Never edit
those copies here; `check:generated` fails when they differ from the release. An Editora release from before
the move (0.28.x and older) has no `user-docs/`, and the script leaves the copies alone. The archived docs of
past releases (`src/content/docs-archive/`) stay here.

### The copy inside the app

`node scripts/build-app-docs.mjs --editora <Editora checkout> --out <folder>` renders the guide for the
copy Editora ships: in a temporary copy of this repo it runs SyncDocs, GenCommands, GenPauta and GenRoadmap
against that checkout, sets `src/lib/version.ts` to its version (`-SNAPSHOT` dropped, as the app's links have it),
builds with `EDITORA_APP_DOCS=1` (`src/lib/app-docs.ts`: only that version's docs, no analytics beacon), and
copies the docs, `/commands`, `/keybindings`, the styles, the icons and the pictures the pages use into
`<folder>`, which Pagefind then indexes. Editora's release workflow runs it from this repo's `master`; the app
serves the folder from 127.0.0.1 and sends any other path on to this site.

`src/lib/commands.ts` (the Commands and Keybindings pages) is generated by
`scripts/GenCommands.java` from Editora's source: `java scripts/GenCommands.java`.
It needs a local checkout of the [Editora](https://github.com/adriandeleon/Editora)
repository (it reads the app's `MainController`, `messages.properties`, and
keymaps). The repo is found as a sibling directory (`Editora-V2` or `Editora`);
override with an argument (`java scripts/GenCommands.java /path/to/Editora`) or
the `EDITORA_REPO` environment variable.

`src/lib/roadmap.ts` (the Roadmap page), the What's New pages, and `src/lib/version.ts` (the app version, from the Editora
`pom.xml`) are generated by `scripts/GenRoadmap.java` from the Editora repo's
`TODO.md`, `CHANGELOG.md`, and `pom.xml`: `java scripts/GenRoadmap.java`. It
finds the Editora checkout the same way as `GenCommands.java`. The output is
committed static data, so the site build needs no access to the Editora repo (it
isn't checked out in CI). Re-run it after bumping the version.

The Pauta conformance page (`src/content/docs/pauta.md`, served at `/docs/v-<version>/pauta/`, with
`/docs/pauta` redirecting to it) is generated by `scripts/GenPauta.java` from the Editora repo's
`src/main/resources/com/editora/pauta.json` and the `pauta.version` of its `pom.xml`:
`java scripts/GenPauta.java`. It lists the edition of [Pauta](https://pauta-project.dev/) the app is working
toward, the conformance that follows from the list, and every rule the app does not meet, grouped by kind, so
the page cannot show a different set from the app's own Pauta window. It finds the Editora checkout the same
way as `GenCommands.java`. Re-run it for each release, from the release tag, like the others: the page
describes the release the docs do, and `check:generated` holds it to that tag's `pauta.json`. Never edit
the page by hand.

`src/lib/whatsnew.ts` (the home "What's new" block) is hand-written: a handful of
highlights taken from the current release's news post. Update it with each release.

The feature pages (`src/content/features/*.md`) are generated by
`scripts/GenFeatures.java`: `java scripts/GenFeatures.java`. It holds each
feature's frontmatter and body and overwrites the Markdown. Edit the content
there (or in the Markdown, then port it back).

## Versioned docs

The docs are versioned: every docs page and per-command page lives under
`/docs/v-<version>/…` (e.g. `/docs/v-1.0.0/editing`), where `<version>` comes
from the committed `src/lib/version.ts`. Bare `/docs` redirects to the current
version, and so does the unversioned slug of every current docs page:
`/docs/<slug>` (e.g. `/docs/editing`) redirects to `/docs/v-<version>/<slug>`
(`/docs/introduction` to the version's landing page, `/docs/v-<version>/`).
Those are the stable links for places outside the site — the Editora README,
news posts — that should always reach the newest text. The redirect list is
generated in `astro.config.mjs` from the files in `src/content/docs/`, so a new
page gets one automatically and a removed page's stops. Only the versioned URLs
are real pages, and each app version pins its own `/docs/v-<appVersion>/…`
links; unversioned per-command URLs are not served.

The routes live under `src/pages/docs/[version]/` (`index.astro`,
`[...slug].astro`, `commands/[id].astro`); each emits one path per served
version. Markdown content is authored with plain `/docs/…` links; a small rehype
plugin in `astro.config.mjs` rewrites them to the versioned base at build time,
so content never hardcodes the version — and for an archived page it rewrites to
*that page's own* version, derived from its file path.

### Past versions stay served

The app deep-links `/docs/v-<appVersion>/…`, so those URLs have to keep working
after a release — and they have to describe the version the reader is actually
running, not whatever the docs say today. Each released version is therefore a
**frozen copy**:

- `src/content/docs/` — the current version (the one you edit).
- `src/content/docs-archive/<version>/` — one directory per past release.
- `src/lib/commands-archive/v<version-with-dashes>.ts` — that release's command
  data, so a command added since then has no page under the old version.
- `src/lib/doc-versions.ts` — the registry tying them together, and the only
  file you edit to add or drop a version.

**Archiving a release.** Do this *before* regenerating for the new version,
while `src/content/docs/` and `src/lib/commands.ts` still hold the outgoing one:

```bash
V=0.9.10                                    # the version being archived
mkdir -p src/content/docs-archive/$V
cp src/content/docs/*.md src/content/docs-archive/$V/
cp src/lib/commands.ts src/lib/commands-archive/v${V//./-}.ts
```

Then add an entry to `ARCHIVED` in `src/lib/doc-versions.ts`, importing that
commands snapshot. Everything else follows from that list: the routes, the
sidebar, the version picker, the "you're reading an archived version" banner,
and the per-version `/commands` redirect.

An archived page is a *record of a release*, which is why it's a copy rather
than a re-render of current content: a later correction must not silently
rewrite what a shipped version claimed. Archived pages are excluded from site
search and carry a canonical link to the current version's equivalent, so they
don't compete with it in search results.

Note the archive collection pins `generateId` to the literal `<version>/<slug>`.
The loader's default id generation slugifies, which eats the dots in a version
number (`0.9.10/lsp` → `0910/lsp`) and silently yields zero matching pages.

## Per-command pages

Every command has its own page at `/docs/v-<version>/commands/<command-id>` (e.g.
`/docs/v-1.0.0/commands/view.toggleReadOnly`), generated by
`src/pages/docs/[version]/commands/[id].astro` from the data in
`src/lib/commands.ts`. The app deep-links these by version + command id. Each
page shows the title, id, description, and per-keymap keybindings, with links
back to the relevant guide and the command list. English-only for now; a locale
dimension can be added later (per-locale command data plus a locale-prefixed
route).

To add long-form prose for a command, drop a Markdown file named after the
command id in `src/content/command-docs/` (e.g.
`src/content/command-docs/view.toggleReadOnly.md`). Its body renders as a
"Details" section on that command's page. Commands without one still get the
generated reference. Quote any frontmatter `title:` that contains a colon.
